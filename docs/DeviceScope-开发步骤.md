# DeviceScope 开发步骤

> 配套文档：[DeviceScope-开发计划.md](DeviceScope-开发计划.md)
>
> - **开发计划**：项目定位、功能范围、系统架构、协议设计、测试计划和最终验收标准。
> - **本文档**：可执行的开发顺序、每一步的任务、交付物和验收方式。
>
> 本文档不使用周计划。步骤按依赖关系排列，完成一个步骤并通过验收后，再进入下一步。
>
> 文档更新日期：2026-11-02

## 1. 执行原则

1. 每一步结束时，仓库必须保持**可构建、可运行、可测试**。
2. 一次只打通一条垂直链路：协议 → 模拟器 → 连接 → 展示 → 控制 → 存储。
3. 先写最小可运行版本，再补异常路径和测试。
4. 新想法先记入 P1，不插队当前 P0 步骤。
5. 每个步骤完成时提交一次 Git，提交信息写清“做了什么、如何验证”。
6. 不在同一个步骤里同时修改协议、界面和数据库。

**每一步的完成定义（Definition of Done）：**

- Linux 下构建通过，没有新增编译警告；
- `ctest` 全部通过；
- 新增或修改的行为有对应测试，或明确说明为什么暂不测试；
- 文档与代码同步；
- 手动走通一次本步骤对应的演示路径。

## 2. 已确定的技术决策

| 项目 | 决策 | 理由 |
|---|---|---|
| 开发平台 | Linux（WSL2）为主；Windows 只做构建和打包验证 | 本机工具链完整，避免双平台并行拖慢进度 |
| Qt 版本 | 6.4.2；Windows 使用相同大版本 | 避免使用 6.5+ 新 API，保证两端一致 |
| 测试框架 | Qt Test + CTest | 已安装、零额外依赖 |
| 趋势图 | QPainter 自绘 | 不引入 Qt Charts，减少打包依赖 |
| 模拟器 | Qt Core + Qt Network，无 GUI | 跨平台，并复用 `proto` 库 |
| 日志 | Qt logging categories + 自定义文件 handler | 不引入 spdlog |
| 协议校验 | CRC32（IEEE 0xEDB88320） | 标准实现，便于测试 |
| 字符串编码 | u16 长度 + UTF-8 | 长度明确，避免 `\0` 截断 |
| 时间戳 | UTC 毫秒（`qint64`） | 便于排序、查询和跨时区展示 |
| 打包 | Linux 用 CPack DEB；Windows 用 windeployqt + ZIP | 满足“至少一个平台可运行发布包” |

CMake 最低版本 3.21，统一使用 `CMakePresets.json` 管理 Linux/Windows 构建。

## 4. 详细步骤

### 步骤 0：工程骨架与构建系统

**目标**：三个目标能构建，客户端能弹出窗口，模拟器能接受 TCP 连接，CTest 能运行。

**任务**

1. 初始化 Git，添加 `.gitignore`（`build/`、`*.user`、`*.db`、`*.log`）、`LICENSE`（项目代码 MIT；Qt 依赖遵循 LGPLv3）。
2. 按开发计划 6.1 创建目录，只建当前真正用到的目录。
3. 根 `CMakeLists.txt`：
   - `project(DeviceScope VERSION 0.1.0 LANGUAGES CXX)`；
   - C++20，`CMAKE_CXX_STANDARD_REQUIRED ON`；
   - `CMAKE_AUTOMOC ON`；
   - 统一输出目录为 `${CMAKE_BINARY_DIR}/bin`；
   - `enable_testing()`。
4. 新增 `cmake/CompilerWarnings.cmake`：GCC/Clang 使用 `-Wall -Wextra -Wpedantic`，MSVC 使用 `/W4`。
5. 建立三个目标：
   - `devicescope_proto`：静态库，先放占位头文件；
   - `devicescope_simulator`：Qt Core + Network，监听 `127.0.0.1:9000`，收到数据原样回显；
   - `devicescope_client`：Qt Widgets，空 `QMainWindow`，标题显示版本号。
6. `tests/` 放一个 Qt Test 占位测试，并通过 `add_test` 接入 CTest。
7. 最小日志：`qInfo()` 输出到控制台。
8. 编写 `CMakePresets.json`：
   - configure preset：`linux-debug`、`linux-release`；
   - build preset 和 test preset 与 configure preset 同名；
   - `binaryDir` 统一为 `${sourceDir}/build/${presetName}`。
9. 编写 `README.md`：Linux 构建命令、Windows 构建前置条件、目录说明。

**交付物**

- 可构建的仓库；
- 空窗口客户端；
- TCP 回显模拟器；
- 占位测试；
- README。

**验收**

```bash
cmake --preset linux-debug
cmake --build --preset linux-debug -j
ctest --preset linux-debug --output-on-failure

./build/linux-debug/bin/devicescope-client
./build/linux-debug/bin/devicescope-simulator --port 9000
# 另一个终端
nc 127.0.0.1 9000
```

- 客户端窗口正常出现；
- 模拟器能回显 `nc` 发送的内容；
- 测试通过；
- 无编译警告。

**注意**

- 不要在这一步引入 Qt Charts、QML、spdlog；
- 客户端和模拟器此时都不需要理解协议；
- 先保证输出路径和构建命令稳定，后面所有步骤都依赖它。

### 步骤 1：协议常量与编解码

**目标**：把开发计划第 7 章的协议设计固化为可编译、可编码、可解码的代码。

**任务**

1. 完成 `docs/protocol.md` 第一版，明确以下未在计划中写死的细节：
   - Magic = `0x4453`（ASCII `"DS"`）；
   - Version = `1`；
   - 报文头固定 **22 字节**，所有多字节字段使用网络字节序（大端）；
   - Header CRC 覆盖前 14 字节（Magic 到 Payload Length）；
   - Payload CRC 覆盖完整负载；
   - 单包负载上限 **1 MiB**，长度字段超过上限按致命错误处理；
   - CRC32 使用多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，结果异或 `0xFFFFFFFF`；
   - 字符串统一编码为 `u16 长度 + UTF-8 字节`。
2. `proto/include/devicescope/protocol/Protocol.h`：
   - 协议常量；
   - `MessageType`、`DeviceState`、`CommandId`、`AckResult` 枚举；
   - `Header` 结构体。
3. `Crc32.h/.cpp`：表驱动实现，提供一次性计算和增量计算接口。
4. `Codec.h/.cpp`：
   - `encode(type, flags, requestId, payload)`；
   - `decodeHeader(QByteArrayView)`；
   - `verifyPayload(header, payload)`。
5. `Message.h/.cpp`：各消息体的结构体和编码/解码函数。
6. 各消息体最低字段要求：

| 消息 | 必需字段 |
|---|---|
| HELLO | 请求：`string clientName`；响应：`u16 deviceId`、`string deviceName`、`u32 capabilities`、`u8 result`。版本协商使用报文头 Version |
| HEARTBEAT | `u64 timestampMs` |
| TELEMETRY | `u64 timestampMs`、`f32 temperatureC`、`f32 pressureKPa`、`f32 rpm`、`u8 deviceState` |
| COMMAND | `u8 commandId`、`u32 parameter`（第一版填 0，预留） |
| COMMAND_ACK | `u8 commandId`、`u8 result`、`string message` |
| ALARM | `u32 alarmId`、`u16 code`、`u8 severity`、`u64 timestampMs`、`u8 state`、`string message` |
| ERROR | `u16 code`、`string message` |

7. 所有解码入口返回明确的错误码或 `Result` 类型，不跨模块抛异常。

**交付物**

- `docs/protocol.md` 第一版；
- `devicescope_proto` 库；
- 编解码 API。

**验收**

- 同一消息经过 `encode` 后能正确 `decode`，字段值一致；
- 负数字段、边界值、空字符串能正确往返；
- 负载恰好 1 MiB 能编码成功，1 MiB + 1 被拒绝。

**注意**

- 编码和解码不要共用同一个“字段写入/读取”函数，避免自环测试掩盖偏移错误；
- 先固定协议，再写客户端和模拟器，避免两边同时改协议。

### 步骤 2：流式解包与协议测试

**目标**：让协议库能处理 TCP 字节流，并用测试证明异常输入不会导致崩溃。

**任务**

1. 实现 `StreamDecoder`：
   - `append(const QByteArray&)`；
   - `next(DecodedMessage&)`；
   - 内部缓冲区上限为两个最大报文，超过即报致命错误。
2. 处理规则：
   - **半包**：数据不足时保留，等待下一次 `append`；
   - **粘包**：一次 `next` 只取一包，循环调用直到返回“数据不足”；
   - **非法 Magic**：丢弃 1 字节并重新同步，记录坏包统计；
   - **不支持版本**：丢弃整包并返回错误；
   - **长度超限**：返回致命错误，由调用方断开连接；
   - **CRC 错误**：丢弃整包，记录错误，继续解析后续数据；
   - **未知类型**：保留头部，负载作为原始字节返回，不崩溃。
3. 增加统计：收包数、坏包数、丢弃字节数、当前缓冲大小、历史最大缓冲。
4. 编写单元测试，覆盖开发计划 11.1 的全部场景：
   - 正常编解码；
   - 1 字节随机分片；
   - 多包连续到达；
   - 超长包；
   - 非法 Magic；
   - 不支持版本；
   - 未知消息类型；
   - CRC 错误；
   - 空负载；
   - 最大合法负载。
5. 黄金向量使用手写十六进制字节数组，并用固定种子做随机分片测试。

**交付物**

- `StreamDecoder`；
- 协议单元测试套件。

**验收**

```bash
ctest --preset linux-debug -R proto --output-on-failure
```

- 所有协议测试通过；
- 随机 1 字节分片与 1000 次随机切分不崩溃；
- 坏包后仍能继续解析后续合法包；
- 测试不依赖客户端或模拟器代码。

**注意**

- 黄金向量不能由被测代码生成，否则同一个编码 bug 会同时污染编码和测试；
- 解包器不要分配与长度字段等大的内存，先检查上限。

### 步骤 3：模拟器基础链路

**目标**：模拟器能作为完整设备端，与协议库配合完成握手、心跳、遥测、命令和报警。

**任务**

1. 实现 `SimulatorServer`（`QTcpServer`）和 `SimulatorSession`（每连接一个会话）。
2. 实现 HELLO 握手：
   - 版本不一致时返回 ERROR 并断开；
   - 握手成功后开始发送遥测。
3. 实现心跳：收到 HEARTBEAT 后原样回一条 HEARTBEAT。
4. 实现遥测生成器：
   - 默认 10 Hz，可配置；
   - 温度、压力、转速使用正弦 + 噪声，随机种子可复现；
   - 设备状态随命令变化。
5. 实现命令处理：START、STOP、RESET，返回 COMMAND_ACK，并改变设备状态。
6. 实现报警：
   - 温度超过上限触发 ALARM（raise）；
   - 温度回落到下限以下触发 ALARM（clear）；
   - 使用滞回区间，避免抖动刷屏。
7. 命令行参数：`--host`、`--port`、`--rate`、`--seed`、`--log-level`。
8. 优雅退出：关闭监听、断开所有会话、刷新日志。
9. 模拟器测试：使用 `proto` 库构造客户端，验证握手、心跳、遥测速率和命令响应。

**交付物**

- 可独立运行的模拟器；
- 模拟器测试。

**验收**

- `--rate 10` 运行 1 分钟，遥测包数量约为 600；
- 版本不一致的客户端被拒绝；
- START/STOP/RESET 返回正确 ACK，设备状态改变；
- 超过阈值产生报警，回落后自动清除；
- 未知消息类型只记录日志，不崩溃。

**注意**

- 模拟器不要使用 GUI，保持可脚本化；
- 时间戳统一用 UTC 毫秒；
- 遥测速率要能从命令行调整，后续稳定性测试依赖它。

### 步骤 4：故障注入

**目标**：模拟器能稳定复现网络和协议异常，为客户端测试和演示提供可控故障。

**任务**

1. 增加标准输入命令控制台（无 GUI 时也能交互）：

| 命令 | 作用 |
|---|---|
| `fault delay <ms>` | 所有响应延迟指定毫秒 |
| `fault split <n>` | 将报文拆成 n 段发送 |
| `fault crc <n>` | 接下来 n 个包故意写坏 CRC |
| `fault drop <n>` | 接下来 n 个包丢弃 |
| `fault disconnect` | 主动断开当前连接 |
| `fault oversize` | 发送长度字段超限的包 |
| `alarm overtemp on/off` | 强制触发/清除过温报警 |
| `rate <hz>` | 修改遥测频率 |
| `status` | 打印当前连接数、发包数、故障状态 |

2. 支持命令行一次性场景参数，例如 `--fault delay=200`、`--fault split=3`，便于自动化测试。
3. 所有故障受随机种子控制，保证可复现。
4. 在 README 或 `docs/test-plan.md` 中记录故障命令和预期现象。

**交付物**

- 故障注入控制台；
- 故障场景说明。

**验收**

- 每个故障命令都能复现预期现象；
- 故障开启时模拟器不崩溃；
- 客户端后续步骤能观察到对应异常（本步骤先验证模拟器侧计数和日志）。

**注意**

- 故障注入是测试工具，不要混入正常业务路径；
- CRC 错误必须真正修改字节，而不是只改标志位。

### 步骤 5：客户端连接骨架

**目标**：客户端能在独立网络线程中建立连接、完成握手、断开并正确回收线程。

**任务**

1. 主窗口布局：
   - 顶部连接栏：地址、端口、连接/断开按钮、状态标签；
   - 中部标签页：实时监控、报警、历史、日志；
   - 底部状态栏：连接状态、收包统计、丢弃计数。
2. 实现 `NetworkClient`（UI 线程门面）和 `ConnectionWorker`（工作线程对象）。
3. 线程模型：
   - `ConnectionWorker` 通过 `moveToThread` 移入 `QThread`；
   - `QTcpSocket`、心跳定时器、超时扫描定时器都在 worker 线程的启动槽中创建；
   - UI 不直接持有 socket。
4. 连接状态机：`Disconnected`、`Connecting`、`Handshaking`、`Connected`、`Disconnecting`、`Error`。
5. 实现 HELLO 握手，握手失败显示明确错误。
6. 实现优雅退出：停止接收、关闭 socket、退出线程、`deleteLater`。
7. 跨线程信号只传值类型（结构体需 `Q_DECLARE_METATYPE` 或使用 Qt 6 自动注册）。
8. 界面只做状态展示，不处理协议细节。

**交付物**

- 可连接模拟器的桌面程序；
- 连接状态与错误提示。

**验收**

- 连续连接/断开 20 次，无崩溃、无线程泄漏；
- 先启动客户端再启动模拟器，不崩溃，并显示连接失败；
- 连接成功后状态栏显示设备信息；
- UI 在连接过程中始终可操作。

**注意**

- 不要在 `ConnectionWorker` 构造函数里创建 socket，那时对象还在 UI 线程；
- 不要继承 `QThread` 并把业务逻辑写进 `run()`。

### 步骤 6：心跳、请求匹配与自动重连

**目标**：连接能检测假死、匹配命令响应、在断线后自动恢复。

**任务**

1. 心跳：
   - 每 2 秒发送一次 HEARTBEAT；
   - 6 秒内没有收到任何数据视为断线；
   - 心跳失败进入重连流程。
2. 请求管理：
   - 客户端生成 `requestId`（从 1 开始，跳过 0）；
   - `QHash<quint32, PendingRequest>` 保存类型、命令、发送时间、超时时间；
   - 单个 100 ms 扫描定时器统一处理超时，不额外创建大量定时器；
   - 收到 COMMAND_ACK 时按 `requestId` 匹配并移除。
3. 超时：
   - 命令默认超时 3 秒，可在请求中覆盖；
   - 超时后界面显示“超时”，并从待处理表移除。
4. 自动重连：
   - 指数退避：1 s、2 s、4 s、8 s、16 s、30 s 封顶，加随机抖动；
   - 稳定连接 10 秒后重置退避；
   - 手动断开不触发重连。
5. 断线处理：
   - 所有未完成请求标记为失败；
   - 清空半包缓冲；
   - 重连成功后重新握手，恢复遥测。
6. 补充连接日志和错误提示。

**交付物**

- 心跳与超时机制；
- 请求匹配；
- 自动重连。

**验收**

- 运行中关闭模拟器，客户端进入重连并在模拟器恢复后自动连上；
- 模拟器延迟响应时，命令状态从“发送中”变为“超时”；
- 并发发送 50 条命令，不会出现 ACK 错配；
- 手动断开后不会自动重连。

**注意**

- 重连后必须清空旧请求，否则旧 ACK 可能匹配到新请求；
- 心跳只用于检测链路，不替代业务请求超时。

### 步骤 7：遥测展示

**目标**：高频遥测下界面保持流畅，内存有界，并显示明确的数据丢弃统计。

**任务**

1. 网络 worker 解码后写入线程安全的有界队列（容量可配置）。
2. UI 使用 50 ms 定时器批量取数据，刷新频率上限约 20 FPS。
3. 队列满时丢弃最旧的遥测样本，并累加 `droppedSamples`；报警和命令不受影响。
4. 实现 `TelemetryTableModel`，展示当前设备快照和最近 N 条样本。
5. 实现 `TrendChart`（QPainter 自绘）：
   - 温度、压力、转速三条曲线；
   - 固定时间窗口（默认 60 秒）；
   - 坐标轴、网格、图例；
   - 开启抗锯齿，但避免每帧重建大量对象。
6. 当前值面板：大字号显示最新温度、压力、转速、设备状态。
7. 暂停/继续刷新；暂停时队列仍然有界，继续时清空积压并恢复实时。
8. 状态栏显示收到的包数、渲染帧率、丢弃样本数。

**交付物**

- 实时遥测表格；
- 趋势图；
- 当前值面板；
- 队列统计。

**验收**

- 模拟器以 100 Hz 发送时，界面仍可拖动和切换标签；
- 连续运行 10 分钟，内存不持续增长；
- 队列积压时丢弃计数增加，界面不卡死；
- 暂停后继续，曲线恢复实时更新。

**注意**

- 不要每收到一个样本就调用 `update()`；
- 表格模型不要为每个样本插入一行，使用快照或环形缓冲；
- 曲线绘制中不要做数据库查询或字符串拼接。

### 步骤 8：控制命令闭环

**目标**：用户能发送命令，并清楚看到发送、确认、失败和超时的全过程。

**任务**

1. 控制面板：启动、停止、复位三个按钮，复位和停止需要确认对话框。
2. 发送命令时：
   - 按钮进入禁用状态，防止重复发送；
   - 生成记录，显示 requestId、命令类型、发送时间。
3. 收到 ACK 后：
   - 更新状态为成功或失败；
   - 记录响应时间和端到端延迟；
   - 恢复按钮状态。
4. 超时后显示明确状态，允许重试。
5. 命令历史列表：时间、命令、状态、延迟、错误信息。
6. 断开或重连时，未完成命令标记为失败。

**交付物**

- 控制命令面板；
- 命令历史；
- 命令状态反馈。

**验收**

- 三种命令均能收到正确 ACK；
- 模拟器拒绝命令时显示失败原因；
- 模拟器不响应时显示超时；
- 连续点击不会产生重复请求。

**注意**

- 不要在 UI 线程等待 ACK；
- 命令状态必须由 `requestId` 驱动，不能只靠按钮状态猜测。

### 步骤 9：报警展示

**目标**：报警能实时展示、自动清除，并与日志和后续存储衔接。

**任务**

1. 报警数据模型：活动报警列表 + 历史报警列表。
2. 表格列：时间、代码、等级（提示/警告/严重）、消息、状态。
3. 按等级使用不同颜色，但保证文字可读。
4. 相同 `alarmId` 的 raise/clear 合并处理，避免重复行。
5. 新报警出现时：
   - 在状态栏显示提示；
   - 可选地切换到报警标签页；
   - 写入应用日志。
6. 报警清除后从活动列表移除，历史列表保留记录。
7. 本步骤先使用内存存储，持久化在步骤 10 接入。

**交付物**

- 活动报警面板；
- 历史报警面板；
- 报警日志。

**验收**

- 模拟器触发过温后，客户端出现报警；
- 温度回落后，报警从活动列表移除；
- 重复报文不会生成重复报警；
- 报警产生和清除都有日志记录。

**注意**

- 报警展示不要被遥测丢弃策略影响；
- 报警去重键使用 `alarmId`，不要只比较消息文本。

### 步骤 10：SQLite 持久化

**目标**：遥测、报警和命令记录可靠落盘，写入不阻塞 UI。

**任务**

1. 数据库位置：`QStandardPaths::AppDataLocation`，允许命令行覆盖。
2. 建立 `StorageWorker` 独立线程，并在线程内创建独立的 `QSqlDatabase` 连接（连接名唯一）。
3. 连接参数：WAL 模式、`synchronous=NORMAL`、`busy_timeout`。
4. 表结构：

```sql
CREATE TABLE schema_version (version INTEGER NOT NULL);

CREATE TABLE telemetry (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id INTEGER NOT NULL,
    ts INTEGER NOT NULL,
    temperature REAL,
    pressure REAL,
    rpm REAL,
    state INTEGER
);
CREATE INDEX idx_telemetry_device_ts ON telemetry(device_id, ts);

CREATE TABLE alarms (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id INTEGER NOT NULL,
    alarm_id INTEGER NOT NULL,
    ts INTEGER NOT NULL,
    code INTEGER,
    severity INTEGER,
    state INTEGER,
    message TEXT
);
CREATE INDEX idx_alarms_device_ts ON alarms(device_id, ts);

CREATE TABLE commands (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id INTEGER NOT NULL,
    ts INTEGER NOT NULL,
    request_id INTEGER NOT NULL,
    command_type INTEGER,
    result INTEGER,
    latency_ms INTEGER,
    message TEXT
);
CREATE INDEX idx_commands_device_ts ON commands(device_id, ts);
```

5. 批量写入：累计 500 行或 1 秒，使用单事务提交。
6. 写入队列有界：遥测可丢弃并计数；报警和命令不可丢弃。
7. 数据库版本表和最小迁移框架。
8. 优雅退出：停止接收、刷空队列、提交事务、关闭连接。
9. 接入步骤 9 的报警和步骤 8 的命令记录。

**交付物**

- 本地历史数据库；
- 批量写入线程；
- 表结构与迁移框架。

**验收**

- 运行 1 分钟后，遥测行数与模拟器发送数基本一致（允许丢弃计数解释差值）；
- 每条遥测不单独提交事务；
- `kill -9` 后数据库仍能打开，WAL 数据可恢复；
- 写入期间 UI 不卡顿。

**注意**

- `QSqlDatabase` 不能跨线程共享，必须在写入线程内创建；
- 不要在主线程执行批量写入或清理任务；
- 表名、列名统一使用小写下划线。

### 步骤 11：历史查询与导出

**目标**：用户能按时间范围查询历史数据，并导出 CSV。

**任务**

1. 历史查询页：
   - 设备、时间范围、指标选择；
   - 分页大小 100/500/1000；
   - 上一页/下一页/总数。
2. 查询在独立线程执行，使用独立的只读连接。
3. 查询使用 `LIMIT/OFFSET`，大结果集禁止一次性加载。
4. CSV 导出：
   - 导出当前查询结果；
   - 使用 UTF-8 BOM，兼容常见表格软件；
   - 导出过程显示进度，支持取消；
   - 导出在后台线程完成。
5. 数据保留策略：
   - 默认保留 7 天，可配置；
   - 启动时和每小时清理一次；
   - 分批删除，避免长事务。
6. 报警和命令记录也支持按时间查询与导出。

**交付物**

- 历史数据查询页；
- CSV 导出；
- 数据保留策略。

**验收**

- 10 万行数据下分页查询响应正常；
- 查询和导出过程中 UI 可操作；
- 导出文件行数与查询结果一致；
- 清理任务不会长时间锁库。

**注意**

- 不要在 UI 线程调用 `QSqlQuery::exec()` 处理大结果集；
- 导出时不要一次性构造整个 CSV 字符串。

### 步骤 12：日志系统

**目标**：运行日志可用于排查连接、协议和存储问题，并能在界面中筛选。

**任务**

1. 使用 `QLoggingCategory` 分类：`app.net`、`app.proto`、`app.db`、`app.ui`、`app.sim`。
2. 自定义 `QtMessageHandler`：
   - 输出到控制台和文件；
   - 按大小轮转（默认 5 MB × 5 个文件）；
   - 加锁，保证多线程写入安全；
   - `QtFatalMsg` 时立即刷新。
3. 应用内日志页：
   - 只读文本视图；
   - 按级别和分类筛选；
   - 暂停/继续、清空；
   - 内存中最多保留 5000 行。
4. 日志导出为文本文件。
5. 原始报文默认只记录头部摘要；完整十六进制转储由调试开关显式开启，并限制长度。

**交付物**

- 文件日志；
- 应用内日志页；
- 日志导出。

**验收**

- 日志文件能按大小轮转；
- 分类和级别筛选有效；
- 多线程同时写入不崩溃、不丢行（允许极少丢失）；
- 默认日志中不出现完整大报文。

**注意**

- 不要在日志中无限保存原始报文；
- 日志页更新同样要节流，避免日志反过来拖垮 UI。

### 步骤 13：故障集成测试

**目标**：用自动化测试覆盖客户端与模拟器的异常交互，证明故障处理不是靠手工演示。

**任务**

1. 集成测试框架：
   - 测试进程启动模拟器（`QProcess`），使用随机端口；
   - 模拟器向标准输出打印 `LISTENING <port>`，测试解析后连接；
   - 每个测试使用独立临时目录和数据库；
   - 使用 `QSignalSpy`、`QTRY_VERIFY_WITH_TIMEOUT` 等待状态变化。
2. 覆盖开发计划 11.2 的集成场景：
   - 连接与握手；
   - 持续接收遥测；
   - 命令与响应匹配；
   - 命令超时；
   - 设备主动断开；
   - 客户端重连；
   - 报警产生和清除；
   - SQLite 批量写入与历史查询。
3. 覆盖开发计划 11.3 的故障注入场景：
   - 延迟发送半个报文；
   - 随机拆分报文；
   - 连续 CRC 错误；
   - 断开网络；
   - 超长长度字段；
   - 延迟命令响应；
   - 高频遥测导致队列积压；
   - 写入过程中关闭程序。
4. 测试必须可在无显示环境下运行（`QT_QPA_PLATFORM=offscreen`）。

**交付物**

- 集成测试套件；
- 故障场景测试结果。

**验收**

```bash
ctest --preset linux-debug --output-on-failure
```

- 集成测试连续运行 10 次无随机失败；
- 每个故障场景都有明确断言，而不是只验证“没崩溃”；
- 无显示环境下可运行。

**注意**

- 测试等待必须带超时，禁止无限等待；
- 不要依赖固定端口，避免并行测试冲突；
- 偶发失败要修复根因，不能简单加重试。

### 步骤 14：稳定性与性能测试

**目标**：用真实数据回答“能跑多久、占多少内存、UI 是否还流畅”。

**任务**

1. 编写稳定性测试脚本或测试程序：
   - 单设备，10 Hz 和 100 Hz 各运行 30 分钟；
   - 每 10 秒记录 RSS、CPU、数据库大小、收包数、丢弃数；
   - 输出 CSV。
2. 检查：
   - 内存是否持续增长；
   - 数据库大小是否受保留策略控制；
   - UI 是否仍能操作；
   - 重连次数和失败次数。
3. 记录关键指标：
   - 空闲 CPU；
   - 100 Hz 下 UI 刷新帧率；
   - 内存峰值；
   - 重连平均耗时。
4. 将原始数据和结论写入 `docs/test-report.md`。

**交付物**

- 稳定性测试脚本；
- 性能数据；
- 测试报告。

**验收**

- 30 分钟运行无崩溃；
- 内存曲线平稳，无持续增长；
- 数据库大小符合保留策略；
- 测试报告包含可复核的原始数据。

**注意**

- 没有实测数据就不要写“性能提升 X%”；
- 测试机器配置和 Qt 版本要写入报告。

## 5. 里程碑检查点

| 里程碑 | 包含步骤 | 应达到的状态 |
|---|---|---|
| M1 协议可用 | 0–2 | 协议库可独立测试，异常输入不崩溃 |
| M2 链路可用 | 3–6 | 模拟器与客户端能稳定通信、重连 |
| M3 核心演示 | 7–9 | 遥测、曲线、命令、报警可完整演示 |
| M4 数据闭环 | 10–12 | 历史数据可写入、查询、导出，日志可排查 |
| M5 可交付 | 13–16 | 故障测试、稳定性数据、双平台构建、文档和视频齐全 |

每个里程碑结束后执行一次完整的 `ctest` 和手动演示，不把问题留到最后一个步骤。

## 6. 变更控制

1. 开发过程中出现的新功能想法，一律先记入 P1，不插入当前步骤。
2. 协议字段变更必须同时更新 `docs/protocol.md`、黄金向量和两端实现；不兼容变更提升 Version。
3. 某个步骤明显超出预期工作量时，删减功能范围，不延长整体周期。
4. Windows 构建问题优先修复构建链，不因此重构业务代码。
5. 步骤 13 之后不再新增 P0 功能，只修复、打包和补文档。
